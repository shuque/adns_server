# Hedged Signatures (ML-DSA, FIPS 204)

Notes on what "hedged" signing means, why FIPS 204 makes it the default for
ML-DSA, and what that means for adns_server's DNSSEC algorithm 18 (ML-DSA-44)
support. Section and algorithm numbers refer to FIPS 204 (August 2024),
`docs/NIST.FIPS.204-MLDSA.pdf`.

## 1. Definition

In a hedged scheme, the per-signature secret randomness (the nonce, or in
ML-DSA the mask) comes from a pseudorandom function of three inputs together:

- secret key material,
- the message, and
- fresh randomness.

The design goal is that hedged signing is **never weaker than deterministic
signing, and stronger whenever the fresh randomness is good**. The term comes
from Bellare et al., "Hedged Public-Key Encryption: How to Protect against Bad
Randomness" (Asiacrypt 2009): you hedge against bad randomness by mixing in
secrets the attacker doesn't have.

FIPS 204 §3.4 frames it this way. For ML-DSA to be secure, the commitment value
**y** must never be used to sign more than one message and must not be easy to
guess. The randomness behind **y** can come from fresh randomness at signing time
or be derived pseudorandomly from the message and a precomputed random value in
the private key. The hedged variant uses **both**: "the use of fresh randomness
during signing helps mitigate side-channel attacks, while the use of
precomputed randomness protects against the possibility that there may be flaws
in the random number generator used by the signer at signing time."

## 2. Where hedging enters ML-DSA

At key generation (Algorithm 6, line 1) a secret 32-octet seed `K` is derived
from the key seed ξ:

```
(ρ, ρ′, K) ← H(ξ || IntegerToBytes(k,1) || IntegerToBytes(ℓ,1), 128)
```

`ML-DSA.Sign(sk, M, ctx)` (Algorithm 2) draws `rnd` and formats the message:

```
 5: rnd ← 𝔹^32        ▷ deterministic variant: rnd ← {0}^32
10: M′ ← BytesToBits(IntegerToBytes(0,1) || IntegerToBytes(|ctx|,1) || ctx) || M
11: σ  ← ML-DSA.Sign_internal(sk, M′, rnd)
```

`ML-DSA.Sign_internal` (Algorithm 7) mixes `rnd` into the mask seed:

```
 6: μ  ← H(BytesToBits(tr) || M′, 64)     ▷ message representative; tr = H(pk)
 7: ρ″ ← H(K || rnd || μ, 64)             ▷ private random seed
    loop κ = 0, ℓ, 2ℓ, ...:
11:   y  ← ExpandMask(ρ″, κ)
12:   w  ← A·y;  w1 ← HighBits(w)          ▷ commitment
      c̃  ← H(μ || w1Encode(w1));  c ← SampleInBall(c̃)
      z  ← y + c·s1
      reject and retry if z or the hint would leak information about the key
```

Notes:

- `rnd` enters at exactly one point, the derivation of `ρ″` (line 7). §6.2:
  "This is the only difference between the deterministic and hedged variant of
  ML-DSA.Sign". §3.4 likewise says the two variants differ only at line 5 of
  Algorithms 2 and 4.
- **Verification is identical** for both variants. A verifier can't tell which
  one produced a signature, and implementing only the hedged variant is enough
  for interoperability (§3.4). The choice has no effect on the DNSSEC wire
  format or on validators.
- `rnd` must be generated inside the cryptographic module that runs
  `Sign_internal` (§5.4). It "should ideally be generated by an approved RBG,
  [but] other methods for generating fresh random values may be used" (§3.6.1).
- This was a deliberate change from the competition submission (Appendix D.2).
  CRYSTALS-Dilithium 3.1 signed deterministically by default, with a fully
  random `ρ′` as the option. FIPS 204 replaced both with the hedged derivation,
  plus an optional deterministic mode where `rnd` is constant.

## 3. Comparison of nonce strategies

| Strategy | Nonce/mask derived from | Fails when |
|---|---|---|
| Randomized (classic ECDSA; Dilithium 3.1's optional mode) | RNG only | The RNG repeats or is biased: the key is lost (e.g. the PS3 ECDSA key, the 2013 Android Bitcoin wallets) |
| Deterministic (RFC 6979, EdDSA, ML-DSA with `rnd = 0^32`) | key + message | The attacker can inject faults or observe side channels (§4) |
| Hedged (ML-DSA default; also XEdDSA, RFC 6979 §3.6 with extra data) | key + message + RNG | Only if the RNG fails **and** the attacker can fault or probe the device |

The hedged row is the point of the construction. Because `K` stays in the
derivation, a broken, repeating, or even attacker-controlled `rnd` reduces
the scheme to the deterministic variant rather than to catastrophe.

This matters for Fiat–Shamir-with-aborts lattice schemes. As with ECDSA,
reusing **y** across two different challenges recovers the key directly:

```
z  = y + c·s1
z′ = y + c′·s1      ⇒   z − z′ = (c − c′)·s1   ⇒   s1
```

A purely randomized ML-DSA, with `ρ″` taken straight from the RNG, would
therefore be as fragile as ECDSA under RNG failure.

## 4. Why FIPS 204 recommends hedged signing

Deterministic signing solves the bad-RNG problem but creates a different
weakness: the attacker can make the signer repeat exactly the same computation,
with the same secret intermediates, as many times as they like. FIPS 204 §3.6.1
says "the primary purpose of rnd is to facilitate countermeasures to
side-channel attacks and fault attacks on deterministic signatures", citing
three papers ([22]–[24] below). It adds: "even a weak RBG may be preferable to
the fully deterministic variants". §3.4 says the deterministic variant "should
not be used on platforms where side-channel attacks are a concern and where
they cannot be otherwise mitigated", and permits it mainly for signers with no
fresh randomness source at signing time.

### 4.1 Differential fault attacks

Get the same message signed twice and inject a fault into one of the two
computations, for example corrupting the challenge `c` after **y** has been
computed. Deterministic signing guarantees both runs share **y**, so the
correct/faulty pair gives the `z − z′ = (c − c′)·s1` relation from §3, and from
it `s1`, which is enough to forge signatures.

- [22] Bruinderink & Pessl, "Differential Fault Attacks on Deterministic
  Lattice Signatures", IACR TCHES 2018(3). Shows this against deterministic
  Dilithium, with essentially a single faulty/correct pair.
- [23] Poddebniak, Somorovsky, Schinzel, Lochter, Rösler, "Attacking
  Deterministic Signature Schemes using Fault Attacks", IEEE EuroS&P 2018.
  Shows it for EdDSA and others, including **software-induced faults via
  Rowhammer**. A fault attack therefore doesn't strictly require physical
  access to the signer.

With hedging, the two runs have different `rnd`, hence different `ρ″` and
**y**. The difference equation then has two unknown masks and reveals nothing.

### 4.2 Side-channel analysis (power / EM / DPA)

Deterministic signing lets an attacker repeat signing operations with
identical secret-dependent intermediates and average the traces. Targets
include the SHAKE call that absorbs `K` to derive `ρ″`, and the arithmetic on
**y** and `c·s1`. Fresh `rnd` makes every run's intermediates different, which
defeats averaging and differential analysis across runs.

- [24] Samwel, Batina, Bertoni, Daemen, Susella, "Breaking Ed25519 in
  WolfSSL", CT-RSA 2018. A side-channel (DPA) attack on the SHA-512-based
  deterministic nonce derivation of Ed25519, the direct analogue of the ρ″
  derivation in ML-DSA.

### 4.3 Message leakage via timing (footnote 3)

With deterministic signing, the number of rejection-sampling iterations is a
fixed function of (key, message), so timing leaks information about the
**message** (not the private key). If the message itself is confidential,
hedged signing should be used (FIPS 204 §3.6.1 footnote 3, citing the
Dilithium 3.1 specification §3.2). DNS RRsets are public data, so this one
doesn't apply to DNSSEC.

## 5. Implications for DNSSEC and adns_server

### 5.1 What we implement

adns_server signs algorithm 18 via
`cryptography.hazmat.primitives.asymmetric.mldsa.MLDSA44PrivateKey.sign(data,
context=None)`: pure ML-DSA with the empty context string required by
draft-westerbaan-dnssec-mldsa. The shared builder is
`adns/crypto.py:mldsa_rrsig_rdata`, used by both online signing and the offline
signer. This is the **hedged** variant.

Verified empirically with cryptography 50.0.0: signing the same input twice
with a fixed key (`from_seed_bytes(bytes(32))`) yields two different, both-valid
2420-octet signatures. The cryptography API (`sign`, `sign_mu`) exposes no
deterministic option, so we can't produce deterministic signatures, including
the draft's §6 example RRSIG (made with `rnd = 0^32`). This is why the alg-18
tests verify signatures rather than compare them to a fixed vector.

### 5.2 Online signing: where hedging matters

The draft's §7.1 points to FIPS 204 §§3.4/3.6 and notes these considerations
apply "especially during online signing". An online signer is a signing oracle
over partly attacker-chosen input:

- With compact denial or RFC 4470 minimally-covering NSEC ("white lies"), the
  attacker picks the qname and therefore the NSEC owner/next-name being signed.
  Every distinct qname is a fresh signing operation.
- Replaying a fixed query triggers re-signing of a fixed RRset. The signature
  cache (`crypto.sign_rrset`, 200 entries, TTL ~46 h) absorbs these, but it is
  cleared on zone reload and restart, and entries are evicted under pressure.

A Rowhammer-capable co-tenant on shared hosting is the realistic fault-attack
model for a network-facing online signer. Hedging is the right choice here.

### 5.3 Offline signing

An offline signer (air-gapped host or HSM, signing a fixed zone) faces a much
weaker threat model. The attacker doesn't choose inputs interactively and
usually can't fault or probe the signing host. Deterministic signing would be
defensible there and would give byte-reproducible `signzone` output. Since
cryptography doesn't expose it, alg 18 is the one algorithm the signer can't
reproduce byte-for-byte:

| Alg | Scheme | Signatures reproducible? |
|---|---|---|
| 8 | RSASHA256 (PKCS#1 v1.5) | Yes |
| 13 | ECDSAP256SHA256 | Yes, via RFC 6979 (hence the `cryptography>=43` floor) |
| 15 / 16 | Ed25519 / Ed448 | Yes (deterministic by construction) |
| 18 | ML-DSA-44 | **No**: hedged; re-signing with identical inception/expiration gives different RRSIG octets |

### 5.4 Operational consequences

- Repeated online answers are byte-stable only while the signature cache holds
  the entry. After eviction, reload, or restart, the same RRset gets a new,
  equally valid RRSIG. Validators don't care.
- Any byte-determinism checks on signer output hold only for algorithms
  8/13/15/16. Alg-18 output must be checked by verifying it.
- Code comments and Design.md should credit FIPS 204, not the draft, with the
  hedged-signing recommendation. The draft only defers to FIPS 204. Currently
  `adns/crypto.py:49-50` and Design.md §11.3 say hedged "is what
  draft-westerbaan-dnssec-mldsa prefers", which overstates the draft.
